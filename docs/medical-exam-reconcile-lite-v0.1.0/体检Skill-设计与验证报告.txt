体检套餐轻量 Skill：设计与实测报告
日期：2026-10-01　版本：medical-exam-reconcile-lite 0.1.0

一、交付结论

已完成独立 Skill 源码与真实测试集运行。它采用“宿主独立看图 → 本地结构化文本 → 确定性核对”的工作方式，运行时只需 Python 3.10+ 标准库。

原项目11项断言测试在新接口上全部通过；新增30项单测全部通过。4份真实Excel的25个sheet解析为68个方案、2413个项目出现次数，与原算法修正读列探测后的参考输出逐项、顺序完全一致。

全部26张原图已独立看像素转录并实际送入新Skill CLI：共72个可见方案、2609个项目，6处截断不确定；26张图均留下处理结果，没有输入异常。业务结果是36个方案需复核候选、30个方案报告差异、6个方案标题未定位，不能表述为“所有方案匹配通过”。

二、定位到的项目

仓库：https://github.com/songlongGithub/CheckProjectInformation
快照：1392fcc2cf9451467b40f0be4e840a274967a481
现有Skill：skills/medical-exam-checker，源码metadata版本1.1.0（README较旧）

这是“Excel体检套餐与机构订单截图的清单核对”，不是疾病诊断或检验指标判读。原项目已有PyQt桌面、FastAPI/Vue网页版及调用百度OCR、可选LLM的Skill。

三、核心逻辑

1. 输入：方案xlsx、订单截图或已有文字、aliases/renames/gender_renames/composites四类业务规则
2. Excel解析：实际A/B/C/E/F对应主项目、子项目、说明、男、女；“项目或组合”开始、“健康管理”停止。沿行状态切分男、女未婚、女已婚及H等类别；通用项目与专属区块组合
3. 名称处理：套餐父项优先，否则子项目优先；先执行解析期重命名/拆项，再按类别做性别重命名；稳定去重和排序
4. 图片读取：宿主独立识别实际显示的方案标题与清单，保留截断/模糊标记；不从Excel预期项补全文字，也不把界面未选中行当成另一份已展示清单
5. 方案定位：清除提示性括号，保留性别/婚姻/主题等限定；按类别筛选并比较标题，阈值95。同分或低分交人工确认
6. 项目核对：精确/别名一对一 → fuzzy候选（阈值85）→ composites包含关系候选 → 缺失、多余。别名是等价；包含关系不等于等价
7. 输出：JSON完整记录及简洁文本。精确/别名计确认配对；fuzzy/composite一律“需复核”。失败、空解析、标题歧义都不能被包装成一致

四、为什么更轻

- 5个运行脚本，共47,089字节；原Skill为12个Python文件、108,529字节
- SKILL.md从17,626字节精简至3,368字节，细节按需读references
- 无pandas/openpyxl/fuzzywuzzy/requests运行依赖，无venv自举、网络客户端、凭据探测或后台服务
- Excel直接读ZIP/XML；字符串分数用标准库实现，并与原Levenshtein评分做真实词表对照
- 内置规则内容未改：43别名对、3重命名、1性别重命名、3组合定义
- 图片识别使用宿主已有视觉能力；脚本本身不把图片发给外部服务

五、本次查出并处理的缺陷

1. 现有Skill按Excel首两行推断列宽，合并标题使前两组表误判为1列，丢失B/E/F。旧core仅得到50方案/1650项。新读取器按真实坐标获取6列，恢复为68方案/2413项；参考测试只修正这个probe，不修改上游源代码或原断言
2. 旧composites可能凭任一子项就消除整个父套餐的缺失。新Skill保留原关系候选，但所有组合覆盖必须复核，不声称套餐已完整
3. 旧聊天摘要可在全部OCR失败时显示“全部完美”。新报告显式保留每个失败，并用退出码2表示输入错误
4. 同分方案原来可能取首个；新Skill不替用户选一个
5. 独立审查发现的畸形Excel异常退出、UTF-16 XML实体检查绕过已修复。同一探针复验，均返回结构化输入错误，无traceback

- 原11项断言：原输入、原expected不变，仅返回形状适配后在新模块执行，11/11通过
- 真实Excel：4/4表、25sheet、68方案、2413项，逐项与顺序均一致
- 原/新评分：94个实际项目名两两比较2种scorer，17,672次，0个差异
- 68个真实方案的基础匹配行为对照通过
- 66个已定位的真实图片方案，原/新匹配对象、顺序与类型逐行相同；明确的行为差异是fuzzy/composite改为待复核，并给组合关系加候选提示
- Skill frontmatter校验通过；所有源码编译通过；引用文件均存在

C. 全量原图主路径（宿主视觉 → CLI）
- 覆盖26/26原图，独立提取72个实际显示方案、2609项，6处截断不确定
- 方案结果：36需复核、30有差异、6未定位；输入错误0
- 已定位部分：1186个精确配对、736个别名配对、364个模糊候选、39个组合候选；另报告29个缺失、49个多余
- 计数是本次提供文本上的项目/结果行出现次数，不是患者数、唯一检查数或医学准确率
- 未定位者包括截图中的方案六、方案七和若干H版本；未强行选用另一Excel方案
- 转录在看Excel预期项之前完成。没有双人独立临床标注金标准；因此这里只声明真实全量运行和算法对照，不能给“图片准确率100%”

D. 本地Tesseract探索路径（如实保留失败）

- 百度兼容提取器只从5图提到方案，且均未定位；21图未提到方案

七、复现与使用

解压后进入medical-exam-reconcile-lite目录：

只查看Excel：
python3 scripts/check.py --excel 方案.xlsx --excel-only --output 方案.json

对已提取的订单JSON核对：
python3 scripts/check.py --excel 方案.xlsx --ocr-json 订单1.json 订单2.json --output 核对.json --text-output 差异.txt

零依赖自测：
python3 -S -m unittest discover -s tests -v

完整原项目重跑步骤在references/verification.md；tests/verify_project.py支持原仓库、独立转录目录和本地OCR目录。退出0是提供文本一致或Excel解析完成；1是差异/待复核；2是输入错误。

本次环境：Linux、Python 3.12.14。用于原项目参考测试的依赖为pandas 2.2.3、openpyxl 3.1.5、fuzzywuzzy 0.18.0、python-Levenshtein 0.23.0、requests 2.34.2、pytest 9.1.1；这些不属于新Skill运行依赖。

八、交付范围与限制

交付含可移植Skill目录、源码、默认规则、合成测试、可复现脚本、脱敏结果和哈希。原图、客户Excel、完整OCR/视觉转录、详细客户报告、凭据和模型文件均未打包。验证时均在本地处理，没有调用百度/外部LLM服务。

未改、提交或推送原仓库，未创建PR，未部署，未全局安装。纯通用清单、不同列模板、异常跨区块套餐等仍需人工确认；本版保留其余上游业务分类假设，不能适配所有机构模板。

该工具检查业务清单一致性，不判断套餐是否医疗上充分，也不构成医学建议或临床验证。
